# EVM3588 / IMX415 实测与交付边界

日期：2026-11-03。使用真实 IMX415，没有合成图、插帧或复制帧凑FPS。数字来自本板，**不引用作者 OV8858 成绩作为本板结果**。可读数值保存在 [EMA3588_METRICS.json](EMA3588_METRICS.json)。

## 环境与布局

- EVM3588 B1，Ubuntu20.04.5，Linux5.10.110，glibc2.31，g++9.4 / C++17。
- IMX415/con7，`/dev/video44`，实测1920×1080、NV12、stride1920、MPLANE API / 一个内存平面，sizeimage3110400。
- CPU另外实测NM12/NV12M，两个内存平面；正确归一化后编码481帧并解码。DMA路径明确拒绝NV12M，不以CPU回退冒充DMA。
- 私有SDK pkg-config：MPP1.3.9、RGA2.1.0、libavformat62.12.102、libavcodec62.28.102、libavutil60.26.102；MediaMTX v1.21.2。源码提交与哈希见 `ema3588/dependencies.lock.json` 及运行包构建记录。
- 源UV起点2073600；MPP stride1920×1088、UV起点2088960、输入3133440字节。RGA执行一次硬件布局拷贝，不称纯零拷贝。
- 通过活动编码进程的文件描述符确认 `/dev/video44`、`/dev/rga`、`/dev/mpp_service` 及DMA heap实际被访问，没有软件编码回退。

## 同条件 ABBA 对照

每轮20秒，顺序CPU→DMA→DMA→CPU；两路均请求1920×1080/60fps、6缓冲、帧队列1、包队列8，H.264 CBR8Mbit/s、GOP60、TCP。每轮使用相同8秒严格软件解码客户端，全部退出0、无解码错误。

厂商ISP/3A配置不变，没有直接改传感器曝光。八次轮前/轮后快照的曝光值均为1406、模拟增益45；这证明采样值匹配，**不表示所有帧的曝光已锁定**。未锁CPU频率和温度，因此小样本差异不外推为所有场景的固定收益。

## 驱动序号缺口：未消除

8秒纯采集得到481帧，活动DQBUF速率60.026FPS、按首末驱动时间戳计算58.060FPS，应用队列丢弃0。记录到16个序号缺口，集中为启动后约62.65ms的一次跳变。此前另一轮同样在约62ms处看到8个缺口，现象并不固定为1个。

CSV显示该跳变时驱动时间戳增量283.36 ms、用户态DQBUF增量16.394 ms。此基线没有经过RGA/MPP/RTSP，因此不足以把问题归因于编码或网络。它提示启动阶段的驱动序号/时间戳需要继续核对；不能凭用户态约60FPS就证明没有实际图像损失，也不能把序号缺口改名成应用主动丢帧而忽略。

C++已把STREAMON移到下游RTSP就绪之后，避免在初始化时过早填满相机队列；本次仍复现缺口，**没有宣称这一改动修复了底层问题**。后续需结合RKISP/CIF帧ID、buffer完成事件和传感器时间戳继续定位，不在本轮刷写内核。

## 正确性、背压与恢复

- 8项离线测试通过；Release测试启用`-UNDEBUG`，避免assert被编译掉。覆盖队列关闭/丢弃、IDR重同步、stride/offset/异常长度及lease移动、拒绝、drain、异常展开。
- 正常两轮DMA均采集/编码/发布1201帧，lease1201/1201归还；所有缓冲归还、释放失败0。
- 80ms编码背压8秒：采集481、编码/发布95、主动丢旧386，lease481/481全部归还；解码通过。这个人为压力成绩不作为正常吞吐。
- 两次客户端重新连接均正常解码。停止本项目MediaMTX后，编码程序按预期以Broken pipe错误退出，lease383/383平衡，不在错误网络上永久挂住。这验证故障退出，不是自动重连发布功能。
- 三次短时反复启停通过，包含SIGTERM正常退出。测试finally恢复了原EdgeVision模型任务；仅控制已确认的原应用，没有关闭无关进程。

## 双端显示与播放器修复

电脑严格解码10秒得到566帧，退出码0、无解码错误；这只是本次解码结果，不能把566/10当作Qt或显示器绘制帧率。实拍截图颜色正常，电脑预览正常。

首次板端HDMI有卡顿：该固件ffplay默认选中`h264_rkmpp`，日志出现slow software conversion和RgaBlit/cvtcolor失败。修改为`-vcodec h264 -threads 2`明确软件解码后，不再新增该转换错误，用户确认HDMI恢复正常、延迟不再持续增长。**C++ MPP硬编码不变；板端播放支路现在是软件解码，不宣称为新的C++硬解实现。**

源码包含无需板端键盘的`--fullscreen`、`--windowed`和`--stop`。Windows窗口默认1280×720，避免超出屏幕。私人截图和完整运行日志保留在忽略目录，不进入源代码或发布包。
